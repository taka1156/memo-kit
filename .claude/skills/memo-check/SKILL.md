# memo-check

lint は HTML と CSS の**書き方**しか見ない。このスキルは、ページを**ブラウザで描画した結果**を見る。
書き手は自分の図を「こう見えるはず」と思い込みやすいので、見る観点を固定し、機械で拾えるものは `tests/visual/check.mjs` に拾わせてから、スクリーンショットを観点ごとに目で確かめる。

使う場面:

- **新しいページを書き終えたとき**（memo-style の「書き終えたら」）: 会話で見せる前・memo-publish で登録する前に必ず。
- **既存のページの見た目を変えたとき**: 図・表・CSS を直したら。文章だけの修正なら省いてよい。
- **頼まれたとき**: 「表示を確認して」「スマホで見て」「色を見直して」。

このスキルは commit / push をしない。直したあとの保存は、呼び出し元の流れ（memo-publish など）に従う。

## 1. 準備（セッションで 1 回）

```bash
cd "$(git rev-parse --show-toplevel)"
npm ci --no-audit --no-fund                 # Playwright（tests/visual/ が使う）
npx playwright install chromium             # ブラウザ。入れられない環境は下の MEMO_CHROME
```

ネットワークの制限で `playwright install` できない環境では、手元にある Chromium の実行ファイルを `MEMO_CHROME` に入れる（例: `export MEMO_CHROME="$(ls /opt/pw-browsers/chromium-*/chrome-linux64/chrome 2>/dev/null | head -1)"`）。どちらも無ければ、ブラウザで確かめられないことをユーザーに伝え、lint の結果と下の観点のうちコードを読んで分かるものだけを確かめて、報告に「描画しての確認はしていない」と書く。

## 2. 自動チェックを流す

```bash
python3 scripts/memo.py preview NAME_または下書き.html -o <スクラッチパッド>/NAME.html
node tests/visual/check.mjs <スクラッチパッド>/NAME.html <スクラッチパッド>/check-NAME
```

スマホ幅 375px・PC 幅 1280px × ライト・ダークの 4 通りで開き、タブは 1 つずつ押し、`<details>` は開いた状態でも確かめる。幅を足すときは `--widths 320,375,768,1280`（600px 未満はスマホとして扱う）。外部への通信は止めているので、Web フォントは代わりのフォントで描画される（文字幅が少し違うので、ぎりぎりの所は余裕を持たせる）。

結果は `[要対応]`（終了コード 1）と `[注意]` に分かれる。

| 出るもの | 意味 | 扱い |
| --- | --- | --- |
| 横スクロールが出る・画面からはみ出す | スクロールできる箱（`overflow-x: auto` の表など）の外で、要素が画面の幅を超えた | 必ず直す |
| コンソールのエラー | JS の例外など（外部への通信の失敗は除いてある） | 必ず直す |
| コントラスト不足（3 未満） | 文字と、実際に下にある背景の比 | 必ず直す（下の「わざとの例外」を除く） |
| コントラストが基準未満 | 本文 4.5・大きい文字（24px 以上、太字なら 18.66px 以上）3 に届かない | 直す。直さないなら理由を報告に書く |
| 文字が重なっている | 別々の文字のかたまりの箱が重なった。回転した要素や、絶対配置のラベルで起きやすい | スクリーンショットで確かめて直す |
| スマホ幅で文字が小さい（10px 未満） | 図のラベルなど | 0.68rem（約 10px）以上にする |
| スマホ幅で押しにくい（24px 未満） | ボタン・タブ・summary の高さか幅が 24px 未満 | 余白を足す |
| `--c-*` は背景とのコントラストが 3 未満 | 線・枠・印の色が背景に埋もれる（WCAG の非テキストのコントラスト） | 色を濃く（ダークでは明るく）する |
| `--c-a` と `--c-b` が似ている／1 型・2 型の色覚では見分けにくい | 色の差（ΔE）が小さい。色覚の違いは Machado ら（2009）の方式でまねている | 色を離すか、色以外（ラベル・線の種類・形・位置）でも区別できるようにする |
| `--c-*` がアクセント色に近い | 操作できる所に見えてしまう | 色を変える |
| 並んだ項目のうち一部だけに色 | リスト・表の行・カードが 3 つ以上並び、一部だけ番号の丸（`is-*`）や左線・枠・背景に色がある | 下の「色の意図」で確かめる。意図を書けないなら色を外す |
| opacity で薄くした文字・背景が画像の文字 | 比を測っていない | スクリーンショットで読めるか確かめる |

`[注意]` は「機械が怪しいと思った所」で、誤検知もある。1 件ずつスクリーンショットで確かめ、直すか、直さない理由を報告に書く。全ページ共通のクイズの表示は見ていない（共通部品の見た目は `tests/visual/shoot.mjs`・`compare.mjs` と `visual.yml` が見る）。

## 3. スクリーンショットを観点ごとに見る

`<出力フォルダ>/<sp|pc>-<light|dark>-NN.png`（縦 1600px ごとに切ってある）を Read で開いて、次を確かめる。機械が拾えない崩れ（線と文字の重なり、意図と違う並び、読みにくい配置）はここでしか見つからない。**SP は必ず全部の切れ端を見る。** PC はライトを全部、ダークは図のある所だけでよい。

### SP（スマホ幅）

- [ ] 左右に 16px 以上の余白があり、横スクロールが出ない（表・コードは箱の中だけで横に動く）
- [ ] 横並びの図が縦積みになったとき、**矢印・「→」などの向きが並びに合っている**（縦に並んだのに「→」のまま、回転させた文字が隣に重なる、などがない。向きを変えるなら CSS で記号だけを差し替え、要素ごと回転させない）
- [ ] 図のラベル・凡例・数値が重ならず、切れず、読める大きさ
- [ ] 2 列・3 列のカードが 1 列になったとき、順番が意味の順のまま
- [ ] ボタンやタブが詰まりすぎず、指で押せる
- [ ] 長い英単語・URL・コードが箱を突き抜けていない

### PC（PC 幅）

- [ ] 本文が最大幅（880px）で中央にそろい、図だけが左右に飛び出していない
- [ ] グリッドの列の高さ・はじまりがそろい、片側だけに大きな空白がない
- [ ] 図の中の線・矢印・目盛りと、ラベルの位置が合っている（線がラベルを貫いていない）
- [ ] 表の列幅が極端でなく、見出しが不自然に折り返していない

### 操作で変わるもの

タブと `<details>` は自動で見ている。それ以外（ステップ送り・シミュレーションのボタン・切り替えボタン）は、Playwright で操作して、**最初・途中・最後の状態**を SP と PC で撮って確かめる。

```bash
node --input-type=module -e "
import { chromium } from 'playwright';
const b = await chromium.launch(process.env.MEMO_CHROME ? { executablePath: process.env.MEMO_CHROME } : {});
for (const w of [375, 1280]) {
  const p = await b.newPage({ viewport: { width: w, height: 900 } });
  await p.route(/^https?:/, (r) => r.abort());
  await p.goto('file://<スクラッチパッド>/NAME.html');
  for (let i = 0; i < 3; i++) await p.click('#次へのボタン');          // ページに合わせて書き換える
  await p.locator('#図の要素').screenshot({ path: '<スクラッチパッド>/state-' + w + '.png' });
}
await b.close();"
```

- [ ] どの状態でも、説明文と図の強調が同じものを指している
- [ ] 状態が変わっても図の高さが大きく跳ねず、ボタンの位置がずれない
- [ ] 最初の状態（何も押していない）でも、何をすればよいか分かる

## 4. 色の妥当性

自動チェックはコントラストと色同士の距離しか測れない。色の**意味**は目で確かめる。memo-style の「色のルール」が前提。

- [ ] **アクセント色の場所**: アクセント色が付いているのは h1・h2 の左線・ざっくり言うとの見出し・段落のリンク・ボタンやタブの操作状態だけ（図・箱・番号の丸・強調の文字に付いていない）
- [ ] **意味のある色だけ**: 色の付いた所はどれも、意味（分類・状態）があるか操作できる。なんとなく目立たせたい所に色を付けていない
- [ ] **色の意図が読み手に分かる**: 色の付いた所ごとに「この色は何を言っているか」を 1 文で言え、その 1 文が凡例・ラベル・見出し・本文のどれかに書いてある。読み手が強調なのか注意なのか分類なのかを推測しないと読めない色は、ただのノイズなので外す
- [ ] **一部だけに色を付けたら、違いを書く**: 並んだ項目（手順・リスト・表の行・カード）の一部だけに色を付けたなら、色の付いた項目と付いていない項目の違いが本文に書いてある。たとえば「使うときの落とし穴」の 4 項目のうち 3 つだけ番号の丸を注意の色にすると、残りの 1 つが軽く見え、なぜ色が違うのかも分からない。全部が同じ種類（全部が注意）なら、見出しで伝わるので色は付けない
- [ ] **凡例・ラベル**: 色の意味が凡例・ラベル・本文のどれかに書いてある。色だけで意味を伝えていない（色覚の違いで見分けにくいと出た組み合わせは、特にラベル・線の種類・形でも区別できること）
- [ ] **一貫性**: ページの中で、同じ色はどこでも同じ意味（ある図で「新しい」を表した色を、別の図で「危険」に使っていない）。共通の意味の色（`--c-ok` 正しい・`--c-ng` 誤り・`--c-warn` 注意・`--c-hl` 今ここ）を別の意味に使っていない
- [ ] **色の名前**: 本文で「青い枠」「赤い線」などと書いたなら、ライト・ダークの両方でその色に見える（ダークで水色になる青を「紺」と書いていない）
- [ ] **ライトとダーク**: `--c-*` をライトとダークの両方で定義していて、ダークで暗すぎる・ライトで薄すぎる色がない。背景を色で塗った箱（`color-mix` など）の上の文字が、両方のモードで読める
- [ ] **意味の色の強さ**: 誤り・危険（`--c-ng`）のような強い色を、ただの区別のために多用していない。分類の色は似た明るさにそろえ、どれか 1 つだけが飛び出して見えない

**わざとの例外**: 色やコントラストそのものを説明するページで「読みにくい例」として見せている所は、直さずに報告に「わざと」と書く（その例のすぐ近くに、悪い例であることが文字で書いてあること）。

## 5. 直して、もう一度

1. 見つかったものを直す。図の作りを変えたら、memo-style の規約（共通部品・色のルール）からはみ出していないか見直す。
2. `python3 scripts/memo.py lint 下書き.html`（または `lint NAME`）→ `preview` → `check.mjs` を流し直す。
3. `[要対応]` が 0 件になり、`[注意]` が全部「直した」か「理由つきで残した」になるまで繰り返す。直した所はスクリーンショットでも見直す。

## 6. 報告

呼び出し元の報告に、次の形で 1〜3 行足す（チェック単独で頼まれたときはこれが報告）。

```
表示の確認: SP 375px・PC 1280px × ライト・ダーク。要対応 0 件。注意 N 件（直した a 件／残した b 件: <理由>）
色の確認: コントラスト OK。<色覚で見分けにくい組み合わせがあれば、どう区別したか>
```
