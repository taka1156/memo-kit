# memo-factcheck

ページに書かれた事実（年号・製品名・仕様・数値・人名・由来など）と専門用語の日本語表記を、**書いた本人ではないサブエージェント**に検証させる。
書き手が自分で答え合わせをすると「合っている理由」を探しがちなので、ページだけを渡して疑ってかからせるのが目的。

使う場面は 2 つ。

- **頼まれたとき**: 「ファクトチェックして」「事実確認して」。
- **push の前（必須）**: メモの本文を新しく作った・変えたときは、commit / push の前に必ず実行する（memo-publish の手順 6.5。memo-from-chat・memo-reference の部分修正もここを通る）。
  - 対象外: 仕組みだけの変更（memo-maintain、スキル・README）、タイトル・タグ・日付だけの変更、このスキルの手順 3 で出典を確かめた修正案をそのまま反映するとき（反映後にもう一度チェックし直さない）。
  - 部分修正のときは、変えた箇所（とそのつながりがわかる前後）だけを対象にしてよい。検証用プロンプトの末尾に「対象範囲: <見出し・箇所>。それ以外は読むだけで検証しなくてよい」と書き足す。
  - 指摘が 0 件ならそのまま push する。指摘があれば、報告して直す内容をユーザーに確認し（手順 4）、直してから push する。
  - ユーザーがその場にいない（スケジュール実行など）ときは、指摘が 0 件のときだけ push する。指摘があれば push せずに止め、報告だけ残す。

## 1. 対象を決める

言われ方に応じて対象のメモを決める。名前とパスは `scripts/memo.py` で引く（パスを自分で組み立てない）。

```bash
cd "$(git rev-parse --show-toplevel)"
python3 scripts/memo.py list          # 日付・名前・タイトル・タグの一覧
python3 scripts/memo.py path NAME     # 実ファイルのパス
```

| 言われ方 | 対象 |
| --- | --- |
| 「〇〇をファクトチェックして」 | そのメモ 1 本 |
| push 前のチェック（memo-publish などから） | これから push するメモ。部分修正なら変えた箇所だけ |
| 「さっきのページ」「このページ」 | 会話内で作った未保存の HTML（作業用ファイル）または直前に登録したメモ |
| 「最近の N 本」「今日追加した分」 | `list` の日付で絞る |
| 「タグ:〇〇 全部」 | `list` のタグで絞る |
| 「全部」 | 全メモ。本数が多い（10 本超）ときは、本数と所要時間の目安を伝えて 1 回だけ確認する |

対象が曖昧なら 1 回だけ確認する。

## 2. サブエージェントを起動する

- **1 メモにつき 1 サブエージェント**。複数あるときは並列に起動する（同時に走らせるのは 5 本程度まで。残りは終わり次第起動）。
- サブエージェントには**メモのファイルパス（HTML と Markdown 版）と下の「検証用プロンプト」だけ**を渡す。Markdown 版のパスは `python3 scripts/memo.py path NAME --md`（Markdown 版は build が作る。clone したばかりで `dist/md/NAME.md` が無いとき、または HTML を変えたあとは、渡す前に `python3 scripts/memo.py build` を実行する。最新かどうかは `build --check` で確かめられる）。未保存の作業用ファイルには Markdown 版がないので、`{MD_PATH}` の行を消して HTML だけ渡す。会話の経緯、書いたときの意図、書き手が自信のある/ない箇所などは渡さない（独立性を保つため）。
- サブエージェントにはファイルを編集させない。報告だけさせる。

### サブエージェントが使えない環境

サブエージェント用のツールが無い場合は、書き手（自分）が同じ手順で直接チェックし、報告の冒頭に **「独立チェックではない（書き手による確認）」** と明記する。黙って代用しない。

### 検証用プロンプト

以下を `{PATH}`・`{MD_PATH}`・`{TODAY}` を埋めてそのまま渡す。

```
あなたはファクトチェッカーです。次の HTML ページを読み、書かれている事実が正しいか検証してください。
ファイル: {PATH}
本文の Markdown 版: {MD_PATH}
今日の日付: {TODAY}

手順:
1. ページ全体（本文・表・年表・コード内のコメント・meta description も含む）を最後まで読む。
   本文は Markdown 版で読むと軽い（HTML から自動生成したもので、中身は同じ）。ただし JS の中にだけある文章
   （タップで出る説明文など）は Markdown 版に入っていないので、HTML の <script> 内の文字列も確認する。
2. 検証できる主張を抜き出す: 年号・日付、製品名・バージョン、仕様・数値、人物・組織とその発言や功績、用語の由来、「最新」「現在」などの時点に依存する記述、コード例が言う動作。
   主観的な評価（「おすすめ」「●の数による比較」など）は対象外。ただし事実のように断定していれば指摘する。
   専門用語の日本語訳・カタカナ表記（英語を直訳しただけの訳語や、書き手が作った訳語など）も抜き出す。広く知られた語だけでなく、一般的でない用語こそ確かめる。
3. 各主張をウェブ検索で確かめる。公式ドキュメント・一次情報（発表記事、仕様書、論文）を優先し、まとめサイトだけを根拠にしない。
   根拠が見つからなければ「根拠不明」とし、推測で「正しい」にしない。
   用語は、日本語の一次情報や定番の資料（公式ドキュメントの日本語版や公式の翻訳、その分野の主要な技術書・記事）で実際に使われている表記かを確かめる。
   あまり使われない訳語や書き手の造語は「用語」として指摘する。英語のままやカタカナの方が通じる場合はそれも示す。
4. ファイルは編集しない。

出力（日本語）:
- 冒頭に「確認した主張: N 件（正しい a / 誤り b / 根拠不明 c / 古い d / 用語 e）」
- 続けて、正しい以外の項目だけを 1 件ずつ:
  - 場所: どのセクション・見出しの、どの記述か（短く引用してよいが 15 語未満）
  - 判定: 誤り / 根拠不明 / 古い（今日時点で情報が更新されている） / 用語（一般的でない訳語・表記）
  - 根拠: 何が正しいかを自分の言葉で。出典 URL を必ず付ける
  - 修正案: ページにそのまま入れられる日本語の書き換え案
- 正しかった項目は件数だけでよい。列挙しない。
```

## 3. 結果を確かめてまとめる

- サブエージェントの指摘も間違うことがある。**「誤り」とされた項目は、修正案を出す前に出典を自分でも開いて確認する。** 食い違ったら両論を併記する。
- メモごとに次の形で報告する。指摘ゼロのメモは 1 行で済ませる。

```
## <タイトル>（NAME）
確認 N 件: 正 a / 誤 b / 根拠不明 c / 古い d / 用語 e
1. [誤り] <場所> — <何が違うか> → 修正案: <書き換え> （出典: URL）
2. [根拠不明] ...
3. [用語] <場所> — <ページの表記> は一般的でない → 修正案: <一般的な表記（英語併記）> （出典: URL）
```

- 最後に出典の一覧（Sources）を付ける。

## 4. 修正する（確認してから）

- **ユーザーに「どれを直すか」を確認してから**直す。全部直してよいと言われたら全部。勝手に直さない。
- 未保存の作業用ファイルなら、そのファイルを直して見せ直すだけ。
- 登録済みのメモなら `memo.py path NAME` のファイルを直し、memo-publish の手順に沿って反映する。直す箇所は Grep で探して前後だけ読み、Edit で置き換える（memo-reference の「部分修正」。ファイル全体を読み直さない）:

```bash
python3 scripts/memo.py lint NAME      # OK になること
python3 scripts/memo.py build          # dist/ で崩れがないか確かめる（コミットするのは src/ の原本だけ）
BRANCH="$(python3 scripts/memo.py config branch)"   # push 先（memo.config.json）
git fetch origin "$BRANCH"              # 遅れていれば rebase
git add -A "$(dirname "$(python3 scripts/memo.py path NAME)")"
git commit -m "Fix memo: <タイトル>（ファクトチェック）"
git push origin HEAD:"$BRANCH"
```

- 修正では事実の記述と用語の表記だけを変え、構成やデザインは変えない。用語を直すときは、同じ語がページ内のほかの箇所（JS 内の文字列・クイズを含む）にも残っていないか Grep で確かめてまとめて直す。`memo:date` は更新しない（作成日のまま）。
- 複数メモを直したときは 1 コミットにまとめてよい（メッセージは `Fix memos: ファクトチェック（N 本）`）。

## 5. 報告

短く伝える: 直したメモと件数、直さなかった指摘（理由つき）、公開 URL（`memo.py url NAME`）。
